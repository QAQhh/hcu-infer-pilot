# Torch Inductor AOT Feedback

Use this only when the optimized Triton kernel is not the user's long-term source of truth because it was generated by Torch Inductor, AOTInductor, `torch.compile`, or a packaged ahead-of-time workflow.

Do not assume every Triton kernel is Inductor-generated. In `summary.md`, first state provenance:

- **Inductor/AOTI evidence**: generated wrapper text, `async_compile.triton(...)`, `template_kernels`, `triton_poi_fused` / `triton_red_fused` names, AOTI package output, `torch._inductor` cache paths, emitted `output_code`, or user-provided compile logs.
- **Not enough evidence**: write `not confirmed` and keep recommendations as hypotheses.
- **Hand-written Triton**: write `not applicable` and do not invent Inductor changes.

Map optimization evidence to the smallest Inductor lever that could reproduce it:

| Optimization evidence | What to write for Inductor/AOT |
|---|---|
| A promoted `DEFAULT_CONFIG`, tile, `num_warps`, `num_stages`, `waves_per_eu`, `matrix_instr_nonkdim`, or `kpack` beat the generated kernel | Recommend adding or prioritizing that shape family in ROCm Triton template heuristics, or seeding the autotune result. Inspect `torch/_inductor/template_heuristics/triton.py`, `torch/_inductor/choices.py`, and `torch/_inductor/select_algorithm.py` when a PyTorch source tree is available. |
| The winning config was likely in the candidate set but Inductor did not select it | Recommend investigating compile-time autotune, benchmark stability, cache keying, and reuse. Inspect `torch/_inductor/runtime/autotune_cache.py`, `torch/_inductor/async_compile.py`, `torch/_inductor/runtime/triton_heuristics.py`, and relevant config knobs. |
| Exhaustive/manual search found a family missing from default search | Recommend expanding the relevant search space only for the observed op/shape/dtype/arch guard, not globally. For ROCm GEMM, check max-autotune search space, backend selection, Origami, and ROCm config pruning/finalization logic. |
| The gain came from source rewrite, fewer `tl.load`/`tl.store`, fewer `ttg.convert_layout`, better vectorization, split-K, reduced barriers/waitcnt, or improved MMAC/MLS lowering | Recommend an Inductor codegen/template/scheduler change rather than only a config change. Tie it to exact IR/ISA evidence and name the affected layer: template body, lowering, fusion/layout scheduling, pointwise/reduction codegen, or graph partitioning. |
| AOTI packaging or runtime behavior changed the result | Recommend checking AOT-specific compile flags and artifact handling. Relevant PyTorch source often includes `torch/_inductor/compile_fx.py`, `torch/_inductor/codecache.py`, and wrapper codegen modules. |

Keep `## Torch Inductor AOT Feedback` short but actionable:

- **Generated-kernel provenance**: what proves this was generated by Inductor/AOTI, or why it is only suspected.
- **Best manual optimization signal**: the one or two promoted changes most likely to matter upstream.
- **Recommended Inductor lever**: a concrete compiler-side adjustment, scoped by op kind, shape range, dtype, target arch, and evidence strength.
- **PyTorch source touchpoints**: cite modules/symbols only after source inspection; do not cite a file just because it sounds related.
- **Validation plan**: regenerate the kernel through Inductor/AOTI with the proposed change and compare correctness, timing, Triton cache IRs, and ISA against this run's champion.

If profiler/KB/ISA evidence is degraded, say which parts are hypotheses. If the best recommendation is "seed an autotune cache entry for this exact generated kernel" rather than "change a heuristic globally", say that.

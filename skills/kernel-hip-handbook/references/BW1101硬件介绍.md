# BW1101 硬件介绍与优化参考

本文档记录当前机器上 BW1101 HCU 的实测硬件信息，作为 `bw1000-hygon-optimizer` 中 BW1000 架构说明的补充。当前机器安装 8 张 BW1101，运行时架构为 `gfx938`。

> 信息来源：本机 `hy-smi`、`lspci`、PyTorch/HIP 运行时、`/usr/local/hyhal/bin/update_ids`。公开资料对 BW1101 型号级峰值算力/带宽披露有限，本文对无法从本机工具直接确认的峰值指标标注为“待官方规格确认”。

## 2. 与 BW1000 文档的关键差异

| 项目 | BW1000 文档值 | 当前 BW1101 实测值 | 优化含义 |
|---|---:|---:|---|
| 目标架构 | `gfx926` | `gfx938` | 编译扩展时要包含 `gfx938`，特殊内建/atomic 分支不能只写 `__gfx936__` 或 `gfx926`。 |
| CU 数量 | 80/88 或 64-80 | 64 | block/grid、occupancy、SM/CU 级并发估算要按 64 CU 重新计算。 |
| 显存 | 64 GB | 144 GiB 可见 | 可以承受更大 batch、关闭 checkpoint 等用显存换吞吐策略，但仍需看 DataLoader/pinned memory。 |
| 显存类型/带宽 | HBM2E / 1.8 TB/s | 待官方规格确认；本机可见 mclk 875 MHz | Roofline 里的带宽峰值不要直接沿用 BW1000 的 1.8 TB/s。 |
| 互联 | HSL 7 ports x8 | HSW 全互联，`x8 320`，任意 HCU 1 hop | 多卡训练优先保持拓扑均衡；HCU 0-3/4-7 按 NUMA 分组绑定 CPU。 |
| 功耗 | 文档中 BW1000A 700 W | 800 W | 长时间训练注意功耗墙、温度和 `perflevel`。 |

## 4. 拓扑与多卡训练建议

`hy-smi --showtopo` 显示：

- 8 张 HCU 两两可达。
- 任意两张 HCU 间 hop 数为 1。
- 链路类型为 HSW。
- HCU 0-3 归属 NUMA 0，HCU 4-7 归属 NUMA 1。

多卡训练建议：

1. `torchrun --nproc_per_node=8` 时，CPU 线程和 DataLoader worker 需要按 NUMA 控制；不要默认放大 OpenCV/BLAS 线程。
2. 建议启动脚本显式设置：

```bash
export OMP_NUM_THREADS=1
export MKL_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
export NUMEXPR_NUM_THREADS=1
export OPENCV_FOR_THREADS_NUM=1
```

3. 如果脚本使用 `numactl --membind`，注意 HCU 0-3 与 HCU 4-7 分属不同 NUMA；错误绑定会放大 DataLoader/pinned memory 问题。
4. 8 卡性能异常时先测 all-reduce，再看 DataLoader 和 `find_unused_parameters`，不要先假定 HSW/RCCL 链路异常。

## 5. HIP 编译与算子优化注意事项

### 5.1 编译目标

当前 PyTorch 运行时显示：

```text
gcnArchName = gfx938:sramecc+:xnack-
```

编译自定义 HIP 扩展时建议包含：

```bash
export PYTORCH_ROCM_ARCH=gfx938
# 或兼容多机型：
export PYTORCH_ROCM_ARCH="gfx926;gfx936;gfx938"
```

如果代码里使用架构宏，需要覆盖 `gfx938`：

```cpp
#if defined(__gfx936__) || defined(__gfx938__)
// BW 新架构上的 fast path
#else
// conservative fallback
#endif
```

Sparse4D 的 deformable aggregation 案例已经验证：只在 `__gfx936__` 下写梯度会导致 BW1101/gfx938 上 `grad_mc_ms_feat` 漏写。

### 5.2 Occupancy 与 launch 配置

BW1101 每卡 64 CU，优化估算时：

```text
active_blocks_per_card ≈ 64 * active_blocks_per_CU
active_waves_per_card  ≈ 64 * active_waves_per_CU
```

建议：

- 不要沿用 BW1000 80/88 CU 的 grid 估算。
- 小 kernel 需要检查 grid 是否足够覆盖 64 CU。
- 高寄存器 kernel 优先看 `__launch_bounds__`、寄存器压力、LDS 使用量，而不是只提高 block size。

### 5.3 显存策略

144 GiB 级显存给训练策略更多空间：

- 可以尝试关闭 checkpoint/recompute，用显存换吞吐。
- 可以做 batch size sweep 摸高吞吐，但要同步记录 loss/mAP 影响。
- DataLoader/pin_memory/NUMA 的 CPU 侧放大仍可能 OOM，不能只看 HCU 显存余量。

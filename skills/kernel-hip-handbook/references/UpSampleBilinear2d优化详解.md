## 1. 前置知识：什么是上采样？

### 1.1 直觉理解

上采样（Upsample）就是**把一张小图放大成大图**。

日常生活中的例子：你有一张 100×100 像素的照片，想把它放大到 200×200 像素。原来只有 10,000 个像素点，现在需要 40,000 个，多出来的 30,000 个像素点的颜色值从哪来？——这就是上采样要解决的问题。

### 1.2 在深度学习中的作用

在神经网络中，上采样常用于：
- **语义分割**：网络先把图片缩小提取特征，再放大回原始尺寸生成逐像素的分类结果
- **目标检测**：特征金字塔网络（FPN）中，将低分辨率的高层特征放大，与高分辨率的浅层特征融合
- **图像生成**：GAN 和扩散模型中，从小的隐空间表示逐步放大生成完整图片

### 1.3 上采样的方法

| 方法 | 原理 | 特点 |
|------|------|------|
| **最近邻插值** | 直接复制最近的像素值 | 最简单，但有锯齿 |
| **双线性插值** | 用周围 4 个像素加权平均 | 平滑，计算适中 ✅ 本文关注 |
| **双三次插值** | 用周围 16 个像素加权平均 | 更平滑，计算较多 |
| **转置卷积** | 通过可学习的卷积核放大 | 灵活，但有棋盘格伪影 |

## 2. 前置知识：什么是双线性插值？

### 2.1 一维线性插值

先理解最简单的情况。假设你知道两个点的值：

```
位置 0: 值 = 10
位置 1: 值 = 20
```

现在想知道位置 0.3 的值是多少？线性插值的做法是**按距离加权**：

```
值(0.3) = 10 × (1 - 0.3) + 20 × 0.3
        = 10 × 0.7 + 20 × 0.3
        = 7 + 6
        = 13
```

越靠近哪个点，那个点的权重就越大。

### 2.2 二维双线性插值

双线性插值是一维线性插值在二维平面上的推广。对于一个待求像素点 P，找到它周围的 **4 个已知像素**（左上、右上、左下、右下），分别进行两次一维线性插值：

```
已知四个像素：
  Q00 ---- Q01          Q00 = 左上角    Q01 = 右上角
   |    P   |            Q10 = 左下角    Q11 = 右下角
   |        |            P   = 待求点
  Q10 ---- Q11

设 P 到左上角的水平距离为 dx，垂直距离为 dy（均为 0~1 之间）

步骤 1：沿水平方向插值
  R0 = Q00 × (1-dx) + Q01 × dx     ← 上边两点
  R1 = Q10 × (1-dx) + Q11 × dx     ← 下边两点

步骤 2：沿垂直方向插值
  P  = R0 × (1-dy) + R1 × dy

合并为一个公式：
  P = Q00 × (1-dx)(1-dy) + Q01 × dx(1-dy) + Q10 × (1-dx)dy + Q11 × dx·dy
```

**关键要记住的**：每个输出像素的值由 4 个输入像素按权重叠加而成，权重由距离决定。

### 2.3 align_corners 参数

这个参数影响坐标映射的方式，也就是"放大后的像素坐标怎么映射回原始小图的坐标"：

**align_corners=True**：输出图的四个角精确对齐到输入图的四个角

```
输入 (3 像素):  0 ---- 1 ---- 2
输出 (5 像素):  0 -- 1 -- 2 -- 3 -- 4

映射：output_coord × (input_size - 1) / (output_size - 1)
  0 → 0.0,  1 → 0.5,  2 → 1.0,  3 → 1.5,  4 → 2.0
```

**align_corners=False**：像素被视为占据一个区域，中心点对齐

```
映射：(output_coord + 0.5) × input_size / output_size - 0.5
```

在优化版本中，两种模式的反向映射公式不同，所以分成了两个 if-else 分支。

## 3. 前置知识：什么是反向传播？

### 3.1 为什么需要反向传播

神经网络的训练过程分两步：
1. **前向传播（Forward）**：输入数据 → 经过网络各层 → 得到预测结果
2. **反向传播（Backward）**：从损失函数出发 → 反向计算每一层的梯度 → 用梯度更新网络权重

上采样层虽然没有可学习的权重，但在反向传播时仍然需要**把梯度传回给前一层**。

### 3.2 双线性插值的反向传播

前向过程：每个**输出像素**是 4 个**输入像素**的加权和。

```
output[h2][w2] = input[h1][w1]     × w00
               + input[h1][w1+1]   × w01
               + input[h1+1][w1]   × w10
               + input[h1+1][w1+1] × w11
```

反向过程：根据链式法则，输出像素的梯度要**按相同的权重分配回**对应的 4 个输入像素：

```
grad_input[h1][w1]     += grad_output[h2][w2] × w00
grad_input[h1][w1+1]   += grad_output[h2][w2] × w01
grad_input[h1+1][w1]   += grad_output[h2][w2] × w10
grad_input[h1+1][w1+1] += grad_output[h2][w2] × w11
```

注意这里用的是 **`+=`（累加）** 而不是 `=`（赋值），因为**一个输入像素可能被多个输出像素引用**。

### 3.3 "多对一"写入问题

这是理解整个优化的关键。上采样是**放大**操作，output 比 input 大。以 2× 上采样为例：

```
input:  2×2 = 4 个像素
output: 4×4 = 16 个像素

每个 output 像素贡献给 4 个 input 像素
→ 16 × 4 = 64 次写入，分配到 4 个 input 像素上
→ 平均每个 input 像素被写入 16 次！
```

当多个线程同时往同一个内存地址写入时，就会发生**写冲突**——这是原始版本的核心性能瓶颈。

## 4. 前置知识：GPU 编程核心概念

### 4.1 GPU 的硬件结构（简化版）

```
┌─────────────────────────────────────────────────────┐
│                      GPU 芯片                         │
│                                                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐              │
│  │   SM 0    │ │   SM 1    │ │   SM 2    │ ... (几十个) │
│  │          │ │          │ │          │              │
│  │ 寄存器文件 │ │ 寄存器文件 │ │ 寄存器文件 │              │
│  │ (65536个) │ │ (65536个) │ │ (65536个) │              │
│  │          │ │          │ │          │              │
│  │ 共享内存   │ │ 共享内存   │ │ 共享内存   │              │
│  │ (48~100KB)│ │ (48~100KB)│ │ (48~100KB)│              │
│  └──────────┘ └──────────┘ └──────────┘              │
│                                                       │
│  ┌─────────────────────────────────────────────────┐  │
│  │               L2 缓存（几 MB ~ 几十 MB）          │  │
│  └─────────────────────────────────────────────────┘  │
│                                                       │
│  ┌─────────────────────────────────────────────────┐  │
│  │           全局内存 / HBM（几 GB ~ 几十 GB）        │  │
│  │             访问延迟：200~800 周期                  │  │
│  └─────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

**SM（Streaming Multiprocessor，流多处理器）** 是 GPU 的基本计算单元。每个 SM 拥有：
- **寄存器文件**：65,536 个 32 位寄存器，由所有线程共享分配。访问延迟接近 0 周期，带宽极高。
- **共享内存**：48KB~100KB 的高速片上内存，同一线程块内的线程共享。
- **执行单元**：实际执行加法、乘法等运算的硬件单元。

### 4.2 GPU 存储层次与访问延迟

理解"为什么有些写法快、有些写法慢"的关键在于 GPU 的存储层次：

| 存储层次 | 大小 | 访问延迟 | 作用域 | 说明 |
|---------|------|---------|-------|------|
| **寄存器** | 每线程几十个 | ~0 周期 | 单线程私有 | 最快，变量默认存这里 |
| **共享内存** | 48~100 KB / SM | ~20 周期 | 线程块共享 | 需手动管理 |
| **L1 缓存** | 128 KB / SM | ~30 周期 | SM 内 | 硬件自动管理 |
| **L2 缓存** | 几~几十 MB | ~200 周期 | 全局 | 硬件自动管理 |
| **全局内存(HBM)** | 几~几十 GB | ~400-800 周期 | 全局 | 最慢，但容量最大 |

**关键启示**：寄存器访问比全局内存快 **数百倍**。如果能把数据放在寄存器里处理，性能会远好于反复读写全局内存。

### 4.3 线程、线程块与网格

GPU 的执行模型是大规模并行：

```
网格（Grid）
├── 线程块 0 (Block 0)        ← 被分配到某个 SM 上
│   ├── 线程 0 (Thread 0)
│   ├── 线程 1 (Thread 1)
│   ├── ...
│   └── 线程 255 (Thread 255)
├── 线程块 1 (Block 1)        ← 可能被分配到另一个 SM 上
│   ├── 线程 0
│   └── ...
└── ...
```

- **线程（Thread）**：最小的执行单元，执行 kernel 代码
- **线程块（Block）**：一组线程（如 256 个），在同一个 SM 上执行，共享该 SM 的共享内存
- **网格（Grid）**：所有线程块的集合，覆盖整个计算任务

**线程块大小的选择很重要**：
- 线程块越大 → 每个线程分到的寄存器越少 → 可能导致寄存器溢出
- 线程块越小 → SM 上可以同时驻留更多线程块 → 但单块内的并行度降低

### 4.4 atomicAdd：原子加法操作

当多个线程需要往**同一个内存地址**写入数据时，必须使用原子操作来保证正确性。

**不用 atomicAdd 的后果**（数据竞争）：
```
假设 memory[0] = 0，线程 A 和线程 B 都想给它加 1

期望结果：memory[0] = 2

实际可能发生：
  时刻1：线程 A 读取 memory[0] = 0
  时刻2：线程 B 读取 memory[0] = 0     ← A 还没写回，B 读到旧值
  时刻3：线程 A 写入 memory[0] = 0 + 1 = 1
  时刻4：线程 B 写入 memory[0] = 0 + 1 = 1  ← 覆盖了 A 的结果！

最终结果：memory[0] = 1  ✗ 错误！
```

**atomicAdd 保证**：读取-修改-写回是一个不可分割的操作，同一时刻只有一个线程能操作该地址。

**atomicAdd 的性能代价**：
- **序列化**：当 N 个线程同时对同一地址做 atomicAdd 时，它们必须**排队**依次执行，相当于变成了串行操作
- **延迟**：每次 atomicAdd 需要 **读取→计算→写回** 整个流程，在全局内存上延迟约 400~800 周期
- **带宽浪费**：即使最终只修改一个数，每次原子操作都要在内存总线上传输完整的缓存行（128 字节）

在现代 GPU（如 NVIDIA Ampere/Hopper）中，atomicAdd 在硬件层面有所优化——它可以在 L2 缓存甚至内存控制器中直接执行加法，不需要数据返回 SM 的 ALU。但当冲突严重时，**排队等待仍然是主要瓶颈**。

### 4.5 Scatter vs Gather 模式

这是理解本次优化的**最核心概念**：

**Scatter（分散写入）**：每个线程**读一个**数据，**写到多个**不同位置

```
线程 0: 读 output[0] → 写入 input[a], input[b], input[c], input[d]
线程 1: 读 output[1] → 写入 input[a], input[b], input[e], input[f]
线程 2: 读 output[2] → 写入 input[a], input[c], input[e], input[g]
         ↑                     ↑
    每个线程读一个      多个线程写同一个地址 → 冲突！
```

**Gather（收集读取）**：每个线程**从多个**位置读取数据，**写一个**结果

```
线程 A: 读 output[0], output[1], output[2]... → 写入 input[a]  ← 只有我写这里
线程 B: 读 output[1], output[3], output[5]... → 写入 input[b]  ← 只有我写这里
线程 C: 读 output[0], output[2], output[4]... → 写入 input[c]  ← 只有我写这里
           ↑                                          ↑
      可以有多个线程读同一地址               每个地址只有一个线程写 → 无冲突！
```

**核心区别**：
- **读操作天然无冲突**——多个线程同时读同一地址完全没问题
- **写操作有冲突风险**——多个线程写同一地址需要原子操作来序列化

因此，**Gather 模式天然避免写冲突，而 Scatter 模式天然容易产生写冲突**。

### 4.6 Grid-stride Loop vs 一线程一元素

**Grid-stride Loop**（原始版本使用）：

```cuda
// 线程总数可能少于数据量，每个线程处理多个元素
for (int i = blockDim.x * blockIdx.x + threadIdx.x;
     i < total_elements;
     i += blockDim.x * gridDim.x) {    // 步长 = 全部线程数
    process(data[i]);
}
```

优点：启动的线程块数量可以少于数据量，灵活性好。
缺点：一个线程可能处理多个不相邻的元素。

**一线程一元素**（优化版本使用）：

```cuda
int i = blockDim.x * blockIdx.x + threadIdx.x;
if (i < total_elements) {
    process(data[i]);
}
```

优点：逻辑简单，编译器更容易优化；每个线程的工作量固定。
缺点：需要启动足够多的线程块来覆盖所有元素。

### 4.7 C10_LAUNCH_BOUNDS_1 与 __launch_bounds__

`C10_LAUNCH_BOUNDS_1(N)` 是 PyTorch 中对 CUDA `__launch_bounds__` 的封装：

```cuda
// 等价于
__launch_bounds__(N)   // 告诉编译器：这个 kernel 最多用 N 个线程/块启动
```

这个注解的作用是**影响编译器对寄存器的分配策略**：

- **设 `__launch_bounds__(1024)`**：编译器知道可能有 1024 线程/块，于是尽量**少用寄存器**，确保 1024 线程能全部驻留在 SM 上。每个线程可用的寄存器数 ≈ 65536 / 1024 = 64 个。
- **不设 launch_bounds**：编译器根据 kernel 的实际代码自由分配寄存器，可能会给每个线程更多寄存器，但导致每个块能容纳的线程数减少。
- **设 `__launch_bounds__(256)`**：每个线程可用寄存器 ≈ 65536 / 256 = 256 个，远比 1024 线程的情况宽裕。

**权衡关系**（非常重要）：

```
线程块越大 → 单线程寄存器越少 → 中间变量可能溢出到全局内存（慢！）
线程块越小 → 单线程寄存器越多 → 中间变量都在寄存器中（快！）
                                但 SM 上的线程总数可能不够饱和
```

这就是为什么优化版本**去掉了 `C10_LAUNCH_BOUNDS_1(1024)` 并把线程块改为 256**——新 kernel 需要更多寄存器（来存储局部累加变量和坐标计算结果），用 256 线程/块可以给每个线程分配更多寄存器空间。

## 5. 原始版本分析：Scatter 模式

### 5.1 原始 backward kernel 的代码逻辑

```
136:200:reference/UpSampleBilinear2d.cu
// Backward (adjoint) operation 1 <- 2 (accumulates)
template <typename scalar_t, typename accscalar_t>
C10_LAUNCH_BOUNDS_1(1024)
__global__ void upsample_bilinear2d_backward_out_frame(
    const size_t nc,
    const int height1, const int width1,    // input 尺寸
    const int height2, const int width2,    // output 尺寸
    const accscalar_t rheight, const accscalar_t rwidth,
    const bool align_corners,
    scalar_t* __restrict__ idata,           // grad_input（要写入的）
    const scalar_t* __restrict__ odata) {   // grad_output（要读取的）
  // ... 遍历 OUTPUT 空间中的每个像素
  for (size_t index = ...; index < o_numel; index += ...) {
    // 1. 从 index 解码出 output 坐标 (h2, w2)
    // 2. 用 area_pixel_compute_source_index 映射到 input 空间，得到 (h1, w1) 和权重
    // 3. 读取 grad_output[index]
    // 4. 用 fastAtomicAdd 把加权梯度写到 grad_input 的 4 个位置
    fastAtomicAdd(idata, ..., h0lambda * w0lambda * d2val, true);
    fastAtomicAdd(idata, ..., h0lambda * w1lambda * d2val, true);
    fastAtomicAdd(idata, ..., h1lambda * w0lambda * d2val, true);
    fastAtomicAdd(idata, ..., h1lambda * w1lambda * d2val, true);
  }
}
```

### 5.2 用图来理解 Scatter 过程

以 2× 上采样为例（input 2×2 → output 4×4）：

```
grad_input (2×2):          grad_output (4×4):
  ┌────┬────┐               ┌────┬────┬────┬────┐
  │ A  │ B  │               │ o0 │ o1 │ o2 │ o3 │
  ├────┼────┤               ├────┼────┼────┼────┤
  │ C  │ D  │               │ o4 │ o5 │ o6 │ o7 │
  └────┴────┘               ├────┼────┼────┼────┤
                            │ o8 │ o9 │o10 │o11 │
                            ├────┼────┼────┼────┤
                            │o12 │o13 │o14 │o15 │
                            └────┴────┴────┴────┘

Scatter 过程（每个 output 像素的梯度"散射"到 4 个 input 像素）：

线程 0 处理 o0 → atomicAdd 到 A, B, C, D
线程 1 处理 o1 → atomicAdd 到 A, B, C, D
线程 2 处理 o2 → atomicAdd 到 A, B, C, D
线程 3 处理 o3 → atomicAdd 到 A, B, C, D
...
线程 15 处理 o15 → atomicAdd 到 A, B, C, D

结果：每个 input 位置（如 A）被 16 个线程的 atomicAdd 竞争！
总共 16 × 4 = 64 次 atomicAdd 操作，但只有 4 个目标地址。
```

### 5.3 原始版本的性能问题

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| **atomicAdd 竞争** | ⭐⭐⭐⭐⭐ | 上采样倍率越高，竞争越严重。4× 上采样时每个 input 位置被 256 线程竞争 |
| **需要预先 zero_()** | ⭐⭐ | Scatter 模式下某些 input 位置可能没有线程写入，必须先初始化为 0 |
| **结果不确定性** | ⭐⭐ | 浮点 atomicAdd 的累加顺序不确定，导致结果位级不可复现（PyTorch 的注释中明确标注了 `Nondeterministic`） |

### 5.4 原始版本的调度代码

```

const size_t num_kernels = nbatch * channels * output_height * output_width;
const int num_threads = std::min(
    at::cuda::getCurrentDeviceProperties()->maxThreadsPerBlock, 1024);
```

注意 `num_kernels` 基于 **output** 尺寸计算——因为每个线程处理一个 output 像素。

## 6. 优化版本分析：Gather 模式

### 6.1 核心思路：反转并行方向

优化版本做了一个思维上的反转：**不再让每个线程负责一个 output 像素去"散射"梯度，而是让每个线程负责一个 input 像素，主动去 output 空间"收集"所有对自己有贡献的梯度。**

### 6.2 用图来理解 Gather 过程

```
同样是 2× 上采样（input 2×2 → output 4×4）：

Gather 过程（每个 input 像素主动"收集"来自相关 output 像素的梯度）：

线程 A 负责 input[0][0]：
  → 搜索哪些 output 像素引用了 input[0][0]
  → 找到 o0, o1, o4, o5（以及可能的 o2, o3 等）
  → 读取这些 output 位置的梯度并累加
  → total_grad = Σ(grad_output[oi] × 权重)
  → idata[A] = total_grad   ← 普通赋值，不是 atomicAdd！

线程 B 负责 input[0][1]：
  → 搜索引用了 input[0][1] 的 output 像素
  → 同样累加后直接赋值

线程 C 负责 input[1][0]：
  → ...

线程 D 负责 input[1][1]：
  → ...

结果：每个 input 位置只有 1 个线程写入，零冲突！
```

### 6.3 Gather 模式为什么可行？

在双线性插值中，每个 input 像素最多影响其周围的一小片 output 区域。以 2× 上采样为例：

```
input 像素 (ih, iw) 影响的 output 范围大约是：
  oh ∈ [ih×2 - 1, ih×2 + 2]
  ow ∈ [iw×2 - 1, iw×2 + 2]

也就是大约 4×4 = 16 个 output 像素的区域（实际通常更小）
```

这个范围与上采样倍率成正比，但总体是一个**有界的小窗口**。线程只需在这个小窗口内搜索即可，**不需要遍历整个 output 空间**。

### 6.4 反向坐标映射的推导

原始的前向映射是：`output 坐标 → input 坐标`

```
align_corners=True:   input_coord = output_coord × scale
align_corners=False:  input_coord = (output_coord + 0.5) × scale - 0.5
```

Gather 模式需要反过来：给定 input 坐标 `(ih, iw)`，求哪些 output 坐标 `(oh, ow)` 在前向插值时会用到这个 input 点。

```
align_corners=True:
  前向：x = oh × scale_h  →  x 落入 [ih-1, ih+1] 区间
  反解：oh ∈ [ceil((ih-1)/scale_h), floor((ih+1)/scale_h)]
  代码中取了更宽松的范围确保不遗漏

align_corners=False:
  前向：x = (oh+0.5) × scale_h - 0.5  →  x 落入 [ih-1, ih+1]
  反解：oh ∈ [ceil((ih-0.5)/scale_h - 0.5), ...]
```

代码中 `oh_start`, `oh_end`, `ow_start`, `ow_end` 就是这个搜索窗口的边界。

### 6.5 优化版本的调度代码

优化版本中，调度代码（host 端）的 `num_kernels` 仍然使用了 output 尺寸（第 394 行），线程块大小也仍在外层使用 1024（第 395~396 行）。但 **kernel 内部逻辑已完全改变**：

- kernel 不再使用 grid-stride loop，每个线程通过 `index = blockDim.x * blockIdx.x + threadIdx.x` 直接映射到 input 空间
- 通过 `if (ih >= height1 || iw >= width1) return;` 进行越界保护——由于 output 尺寸 > input 尺寸，会有部分线程直接退出

这意味着启动的线程数多于 input 像素数，部分线程空转。一种更优的做法是将 `num_kernels` 改为 `nbatch * channels * input_height * input_width`，但当前实现通过边界检查保证了正确性。

> **注**：如果你在其他代码库中看到类似优化的"更彻底"版本，调度代码中的 `num_kernels` 和 `num_threads` 也会相应调整为 input 尺寸和 256。

## 7. 逐项优化详解

### 7.1 优化一：Scatter → Gather 反转（核心，消除 atomicAdd）

**这是所有优化中收益最大的一项**，预期带来数倍的性能提升。

| 维度 | 原始版本（Scatter） | 优化版本（Gather） |
|------|-------------------|------------------|
| **并行粒度** | 每线程 1 个 output 像素 | 每线程 1 个 input 像素 |
| **总线程数** | batch × C × outH × outW | batch × C × inH × inW |
| **读操作** | 每线程读 1 个 odata | 每线程读 ~(2/scale)² 个 odata |
| **写操作** | 每线程 4 次 atomicAdd | 每线程 1 次普通赋值 |
| **写冲突** | 严重（上采样倍率越高越严重） | **完全没有** |
| **需要 zero_()** | 是 | 否 |
| **结果确定性** | 不确定（atomicAdd 顺序随机） | **确定**（每个位置唯一线程） |

**为什么 Scatter 慢，Gather 快？**

用一个生活类比：

> **Scatter 像寄快递**：16 个快递员（线程）都要往同一个地址送包裹（atomicAdd）。门只有一个，必须排队，一个个进去放包裹。即使快递员很多，排队等着进门的时间占了绝大部分。
>
> **Gather 像拿快递**：4 个收件人（线程）各自去不同的快递柜取自己的包裹。虽然有些快递柜同时被多人路过（读不冲突），但每个人最终只往自己家里放（写不冲突）。完全并行，无需排队。

**性能差距的量化估算**：

对于 4× 上采样（input 64×64 → output 256×256）：
- 原始版本：256×256 = 65536 个线程，每个做 4 次 atomicAdd，共 262,144 次原子操作，目标只有 64×64 = 4096 个地址，平均每个地址被 64 次原子操作竞争
- 优化版本：4096 个线程，每个做一个小窗口（约 5×5=25 次读取 + 1 次写入），完全没有原子操作

原子操作竞争的等待时间 ≫ 小窗口额外读取的时间，所以 Gather 通常快很多。

### 7.2 优化二：寄存器内局部累加

```cuda
// 优化版本第 164 行
float total_grad = 0.0f;  // 寄存器中的局部变量

// 在双层循环中不断累加
for (int oh = oh_start; oh <= oh_end; oh++) {
    for (int ow = ow_start; ow <= ow_end; ow++) {
        // ... 判断当前 input 点是否是插值的邻域点 ...
        if (match) {
            total_grad += odata[...] * weight;  // 累加到寄存器变量
        }
    }
}

// 最后一次性写回全局内存
idata[index] = total_grad;
```

**为什么这很重要？**

在原始版本中，每次 `fastAtomicAdd` 都需要：
1. 从全局内存读取当前值（~400 周期）
2. 在 ALU 或内存控制器中做加法
3. 把结果写回全局内存（~400 周期）
4. 如果有冲突，还要等待其他线程完成

在优化版本中，`total_grad` 是一个 `float` 局部变量，**存在寄存器中**：
1. 累加操作：从寄存器读（~0 周期）→ 加法 → 写回寄存器（~0 周期）
2. 循环结束后只做 1 次全局内存写入

**延迟对比**：

```
原始版本（假设 16 个 output 贡献到一个 input 点）：
  16 次 atomicAdd × (~800 周期/次，含冲突等待) ≈ 12,800 周期

优化版本：
  16 次寄存器累加 × (~1 周期/次) + 1 次全局写入 × (~400 周期)
  ≈ 416 周期

加速比 ≈ 30×（理论上限，实际取决于缓存命中率）
```

### 7.3 优化三：反向坐标映射 + 邻域窗口裁剪

```cuda
// 优化版本 第 171~178 行
int oh_start, oh_end, ow_start, ow_end;
if (align_corners) {
    oh_start = max(0, (int)ceilf((ih-1) / scale_h));
    oh_end = min(height2-1, (int)ceilf((ih + 2) / scale_h + 3));
    ow_start = max(0, (int)ceilf((iw-1) / scale_w));
    ow_end = min(width2-1, (int)ceilf((iw + 2) / scale_w + 3));
```

**为什么需要窗口裁剪？**

Gather 模式的一个潜在问题：如果每个线程需要遍历**整个** output 空间来找有贡献的像素，那计算量就太大了。

但由于双线性插值的**局部性**——每个 input 像素最多影响周围一小片 output 区域——我们可以精确计算出这个范围，只在窗口内搜索。

**窗口大小与上采样倍率的关系**：

| 上采样倍率 | 窗口大小（约） | 窗口内像素数 |
|-----------|-------------|-------------|
| 2× | 约 4×4 | 约 16 |
| 4× | 约 6×6 | 约 36 |
| 8× | 约 10×10 | 约 100 |

窗口内还有一层 if 判断（检查 `idx(...) == ihw`），进一步剔除不匹配的像素。

**为什么窗口边界用 `ceilf` 和略微宽松的范围（+3）？**

宁可搜索范围稍大一点（多检查几个不匹配的像素），也不能遗漏真正有贡献的像素。遗漏会导致梯度计算错误。多检查几个像素只是浪费一点计算，但缺失梯度是致命的正确性问题。

### 7.4 优化四：移除 C10_LAUNCH_BOUNDS_1(1024)

```cuda
// 原始版本
C10_LAUNCH_BOUNDS_1(1024)    // 告诉编译器：最多 1024 线程/块

// 优化版本
//C10_LAUNCH_BOUNDS_1(1024)   // 注释掉了
```

**深入理解 launch_bounds 的影响**：

GPU 编译器（NVCC）在编译 kernel 时，需要决定每个线程使用多少个硬件寄存器。这个决策受 `__launch_bounds__` 直接影响：

1. **设了 `launch_bounds(1024)`**：
   - 编译器假设每个线程块最多 1024 个线程
   - SM 有 65536 个寄存器 → 每线程最多 65536/1024 = **64 个**寄存器
   - 如果 kernel 实际需要 80 个寄存器，编译器就被迫把 16 个变量溢出到本地内存（即全局内存，慢！）

2. **注释掉 launch_bounds**：
   - 编译器根据 kernel 代码自行估算最优寄存器数
   - 如果编译器判断需要 80 个寄存器，它可以直接分配 80 个
   - 代价是每线程块的最大线程数降低（65536/80 ≈ 819 线程/块）
   - 但由于实际只用 256 线程/块，这完全不是问题

**为什么优化版本需要更多寄存器？**

优化版本的 kernel 新增了这些变量，都需要占用寄存器：
- `total_grad`：局部梯度累加器
- `oh_start, oh_end, ow_start, ow_end`：窗口边界
- `x, y, x0, y0, x1p, y1p, dx, dy`：循环体内的坐标和权重
- `scale_h, scale_w`：缩放因子
- `ihw`：当前 input 像素的线性索引
- 循环变量 `oh, ow`

这些变量在 for 循环中同时活跃，如果被限制为 64 个寄存器，很可能溢出。注释掉 launch_bounds 让编译器自由分配，避免了不必要的溢出。

### 7.5 优化五：线程块大小的选择

在优化版本中，调度代码的线程块大小虽然外层仍写为 1024，但 kernel 内部移除了 `C10_LAUNCH_BOUNDS_1(1024)` 的编译约束，让编译器不再被迫按 1024 线程/块来压缩寄存器。

在一般的 Gather 类 kernel 设计中，推荐将线程块大小设为 **256**，理由如下：

**原因 1：寄存器压力降低**

| 配置 | 线程/块 | 每线程可用寄存器 | 溢出风险 |
|------|--------|----------------|---------|
| 1024 线程 + launch_bounds(1024) | 1024 | 64 | 高（新 kernel 变量多） |
| 256 线程 + 无 launch_bounds | 256 | 256 | 极低 |

256 线程/块时，每个线程理论上最多可用 256 个寄存器（65536/256），远超 kernel 的实际需求。编译器有充足的寄存器空间，完全不需要溢出。

**原因 2：占用率平衡**

占用率并不是越高越好。GPU 性能的关键是**有足够的活跃 Warp 来隐藏内存访问的延迟**，通常 50% 的占用率就足够了。

```
256 线程/块 = 8 个 Warp/块

假设 SM 最多驻留 64 个 Warp：
  每块 8 Warp → 最多 8 个块驻留 → 64 个 Warp → 100% 占用率
  (实际取决于寄存器和共享内存的使用量，但 256 线程/块通常能达到不错的占用率)

1024 线程/块 = 32 个 Warp/块：
  每块 32 Warp → 最多 2 个块驻留 → 64 个 Warp → 100% 占用率
  但如果因为寄存器溢出导致实际需要更多寄存器，可能只能驻留 1 个块 → 50% 占用率
```

**原因 3：调度灵活性**

更小的线程块意味着更多的线程块总数，GPU 调度器可以更灵活地将它们分配到各个 SM 上，实现更好的负载均衡。

### 7.6 优化六：内联坐标映射（消除函数调用）

```cuda
// 原始版本：调用辅助函数
const accscalar_t h1r = area_pixel_compute_source_index<accscalar_t>(
    rheight, h2, align_corners, /*cubic=*/false);

// 优化版本：直接内联公式
if (align_corners) {
    x = oh * scale_h;            // align_corners=true 的映射公式
} else {
    x = (oh + 0.5f) * scale_h - 0.5f;  // align_corners=false 的映射公式
}
```

**为什么内联更好？**

1. **消除函数调用开销**：`area_pixel_compute_source_index` 是一个通用辅助函数，内部有 if-else 分支来处理 `align_corners` 和 `cubic` 参数。在 kernel 的热循环（for 循环）内部频繁调用它，每次调用都要做分支判断。

2. **编译器优化友好**：内联后编译器可以直接看到完整的计算流程，更容易做常量传播（`align_corners` 在整个 kernel 执行期间不变）和循环不变量外提。

3. **Gather 方向的特殊性**：原始的 `area_pixel_compute_source_index` 是前向映射（output→input），但 Gather 模式需要在 output 空间遍历并做前向映射来验证哪个 input 像素被引用。直接内联公式避免了在反方向上"反向使用"一个正方向的函数带来的混乱。

### 7.7 优化七：确定性结果（附带收益）

原始版本在 PyTorch 中注册时有这样一行：

```
931:931:reference/UpSampleBilinear2d.cu
globalContext().alertNotDeterministic("upsample_bilinear2d_backward_out_cuda");
```

这意味着原始版本**无法保证结果的位级可复现**——每次运行，由于 atomicAdd 的执行顺序不同，浮点累加的舍入误差也不同。

注意：优化版本（第 863 行）仍保留了这行声明，但实际上由于 Gather 模式已消除了 atomicAdd，结果已经是确定性的。这可能是开发者尚未清理的遗留代码。

### 7.8 优化八：消除 grad_input.zero_() 预处理

```cuda
// 原始版本在 kernel 启动前必须做：
grad_input.zero_();   // 将整个 grad_input 清零

// 原因：Scatter 模式下，某些 input 位置可能没有任何 output 像素映射到它
// （在下采样或特殊缩放比例下可能发生），如果不清零，这些位置会残留垃圾值
```

优化版本中每个 input 像素都有一个线程处理，即使该像素不被任何 output 像素引用，`total_grad` 也会保持初始值 0.0，最终 `idata[index] = 0.0` 等效于清零。

**消除 zero_() 的意义**：
- `zero_()` 需要遍历整个 grad_input 张量，写入全零值。对于大张量这是一次完整的内存写操作。
- 优化版本把"清零"和"梯度计算"合并到了一个 kernel 中，减少了一次内存遍历。

## 8. 优化总结与性能预期

### 8.1 优化全景对比

| 维度 | 原始版本 | 优化版本 |
|------|---------|---------|
| **算法模式** | Scatter（分散写入） | Gather（收集读取） |
| **并行粒度** | 每线程一个 output 像素 | 每线程一个 input 像素 |
| **写操作** | 4 次 fastAtomicAdd / 线程 | 1 次普通赋值 / 线程 |
| **写冲突** | 严重（正比于上采样倍率²） | 零冲突 |
| **累加方式** | 全局内存上原子累加 | 寄存器内局部累加 |
| **launch_bounds** | 1024（强制限制寄存器） | 注释掉（编译器自由分配） |
| **线程块大小** | 1024（调度代码） | 1024（调度代码未改，但编译器无 launch_bounds 约束，实际寄存器更宽裕） |
| **结果确定性** | 不确定 | 确定 |
| **需要 zero_()** | 是 | 否 |
| **坐标映射** | 调用辅助函数 | 内联公式 |

### 8.2 各优化手段的预期收益

| 排名 | 优化手段 | 预期收益 | 原理 |
|------|---------|---------|------|
| 1 | **Scatter → Gather** | ⭐⭐⭐⭐⭐ | 消除所有 atomicAdd 竞争，这是性能提升的根本来源 |
| 2 | **寄存器内局部累加** | ⭐⭐⭐⭐ | 把数百次全局内存原子操作变成数百次寄存器操作 + 1 次内存写入 |
| 3 | **窗口裁剪** | ⭐⭐⭐ | 保证 Gather 模式每线程只搜索必要的小邻域，计算量可控 |
| 4 | **移除 launch_bounds(1024)** | ⭐⭐ | 取消编译器对寄存器的强制压缩，避免溢出到慢速内存 |
| 5 | **内联坐标映射** | ⭐⭐ | 消除热循环中的函数调用开销 |
| 6 | **消除 zero_()** | ⭐ | 减少一次全量内存写入 |
| 7 | **结果确定性** | — | 不直接影响性能，但提升可调试性 |

### 8.3 一句话总结

> **将反向传播从"每个 output 点散射梯度到 input"翻转为"每个 input 点收集来自 output 的梯度"，从根本上消除了原子操作竞争——这是 GPU 编程中经典的 Scatter→Gather 优化模式，在上采样 backward 这种"多对一"写入场景中效果尤为显著。**

### 8.4 适用场景与局限

**最适合的场景**（优化收益最大）：
- 上采样倍率高（4×、8× 等）——atomicAdd 竞争越严重，Gather 的优势越明显
- batch size 和 channel 数较大——数据量大时延迟隐藏效果更好
- input 尺寸不太小——确保有足够的线程来饱和 GPU

**需要注意的场景**：
- 上采样倍率为 1×（即 input=output 尺寸相同）——代码已有特殊处理，直接 copy
- 极大的上采样倍率（如 32×）——Gather 模式每线程的搜索窗口变大，计算量增加。但由于原始版本的 atomicAdd 竞争同样急剧恶化（每个 input 点被 1024 个线程竞争），Gather 仍然更优
